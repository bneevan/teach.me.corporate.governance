Tooling, Sandboxing & Protocol Design

Your tangible win: design secure, reliable agentic tool execution pipelines using strict JSON Schema contracts, capability-based isolation, idempotency keys, and sandboxing—grounded in the corporate governance principles of Segregation of Duties and Procedural Authority Limits.

First, retrieve—not reread

From memory: in Lesson 01 and Lesson 02, why does corporate governance strictly forbid a single person from both generating financial invoices and approving bank wire disbursements? What is this principle called?

Review the Governance Principle

This is the Segregation of Duties (SoD). Combining initiation, authorization, custody, and reconciliation in a single role creates unmanageable agency risk, fraud opportunities, and unmonitored error propagation. In agent systems, giving an LLM a single unconstrained tool (like an arbitrary bash terminal or unauthenticated database writer) creates the identical structural failure mode.

1. What Is a "Tool" to an LLM?

An LLM does not execute software code directly. When an agent "uses a tool", it is participating in a structured protocol across four distinct steps:

  1. Declaration: The host application provides tool definitions in the system prompt formatted as JSON Schemas (specifying the function name, description, and strongly typed parameter objects).
  2. Model Emission: Rather than emitting natural language text, the LLM generates a structured JSON payload targeting a specific tool: {"name": "fetch_balance", "arguments": {"account_id": "ACC-904"}}.
  3. Deterministic Validation & Execution: The host application (not the model) parses the arguments, checks authorization permissions, executes the native Python/Go code inside an isolated environment, and captures the output.
  4. Observation Injection: The host app serializes the tool result into a message with role tool (or observation) and returns it to the model's context window for the next reasoning step.
Key Architectural Reality: The model merely proposes an action payload; the host runtime retains complete sovereign authority over whether, where, and how that action executes.

2. JSON Schema Contracts: Rejecting Hallucinations at the Boundary

Unconstrained string inputs are a primary source of agent failure. If a tool accepts arbitrary strings without validation, the model will inevitably inject malformed parameters, SQL injections, or hallucinated enum values.

Production agent architectures enforce Pydantic or JSON Schema validation at the API gateway before the tool implementation is ever touched:

# Example: Strict schema contract using Pydantic
from pydantic import BaseModel, Field, conint
from enum import Enum

class TransferPriority(str, Enum):
    STANDARD = "standard"
    EXPEDITED = "expedited"

class WireTransferInput(BaseModel):
    destination_iban: str = Field(..., regex=r"^[A-Z]{2}\d{2}[A-Z0-9]{1,30}$", description="Valid ISO IBAN")
    amount_cents: conint(gt=0, le=5000000) = Field(..., description="Amount in USD cents (Max $50,000 per tx)")
    currency: str = Field("USD", regex=r"^USD$", description="Supported currency code")
    priority: TransferPriority = TransferPriority.STANDARD
    idempotency_key: str = Field(..., min_length=36, max_length=36, description="Client-generated UUID v4")

If the model outputs amount_cents: -500 or currency: "EUR", the host runtime immediately intercepts the schema violation and feeds back a structured error message to the model ("ValidationError: amount_cents must be > 0") without executing any external side effects.

3. Translating Segregation of Duties into Agent Capabilities

In enterprise governance, internal controls divide workflows into distinct roles so no single entity can initiate and finalize a material commitment without independent scrutiny (Lesson 03). In agent systems, this principle governs tool permissions.

Corporate Governance Control Agent Architectural Counterpart Concrete System Implementation
Segregation of Duties (SoD) Read vs. Mutate Tool Separation Separate inquiry tools (read_ledger) from execution tools (execute_payout). An agent drafting transactions cannot possess write credentials.
Delegated Financial Limits Hard Parameter Ceilings Strict bounds in tool schemas (e.g. max_budget = $5,000). Transactions above the threshold automatically require human confirmation.
Dual-Key / Four-Eyes Principle Multi-Agent Approval Gate A "Proposer Agent" generates the transaction payload; a distinct "Auditor Agent" with an independent prompt and schema verifies compliance before release.
Statutory Audit Trail Immutable Tool Call Logs Logging raw prompt, model output JSON, input args, executed bytecode hash, timestamp, and host response to a write-only log sink.

4. Idempotency Keys: Solving the Network Blindspot

One of the most dangerous failure modes in autonomous systems is the Network Blindspot:

  1. The agent calls charge_credit_card(user_id=12, amount=100).
  2. The payment gateway successfully debits $100 from the user's account.
  3. However, before the gateway returns HTTP 200 OK, the network drops or times out.
  4. The agent receives an HTTP 504 Gateway Timeout error.
  5. Seeing an error, the agent's ReAct loop retries the tool call: charge_credit_card(user_id=12, amount=100).
  6. The customer is billed twice.
The Architectural Fix: Mandatory Idempotency Keys.
Every mutating tool interface must require a client-generated idempotency_key (typically a deterministic UUID generated from the plan step ID or session hash). When the gateway receives a retry with the same key, it returns the cached original result instead of executing the charge again.

5. Capability-Based Sandboxing & Blast Radius Containment

If an agent generates and executes shell commands, code scripts, or file edits, executing them in the host application's native environment is an unacceptable security failure. Enterprise agents use a hierarchy of sandboxing environments to contain the blast radius:

                                                        │
                      2. Spawns Ephemeral Sandbox       ▼

│             ISOLATED SANDBOX WORKSPACE (DATA PLANE)              │
│                                                                  │

The Three Golden Rules of Agent Sandboxing

  • 1. Ephemeral Workspaces: Spin up fresh, clean sandbox environments per session or per task, and tear them down immediately upon task completion so malicious scripts cannot persist across user sessions.
  • 2. Network Egress Filtering: By default, disable all public internet access inside code execution sandboxes. Only whitelist the precise API endpoints required for the task to prevent data exfiltration.
  • 3. Resource Hard Limits: Impose strict kernel-level limits (cgroups) on memory, CPU, and execution duration (e.g. timeout 10s) to prevent fork-bombs and runaway infinite loops from exhausting server hardware.
